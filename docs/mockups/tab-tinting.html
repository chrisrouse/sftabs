The implementation catch for A. Recoloring Salesforce's real favicon means drawing it to a canvas, and the icon is served cross-origin — which taints the canvas and makes toDataURL() throw. The fix is to fetch() it first (we already hold host permissions for these domains), turn it into a blob URL, and draw that. Worth knowing before choosing A, because it is the difference between "set an attribute" and "fetch, decode, composite, re-encode, and watch for Lightning replacing it again".

Option B has no such problem: we draw our own SVG, so there is nothing to fetch.
Both need a watcher. Lightning rewrites <link rel="icon"> on navigation, so whichever we choose has to be reapplied from a MutationObserver on <head> — the same shape as the tab-bar observer we already run.

The one that decides whether this ships. theme.reset() always returns the window to Firefox's default theme — not to whatever theme the user had installed. That is a known Firefox bug (1415267), and there is no way around it: theme.getCurrent() returns an empty object for a user-installed static theme, so we cannot capture one to put back.

So: harmless for anyone on Firefox's built-in light or dark theme, and destructive for anyone running a custom theme — their theme would vanish the first time we colored a window and would not come back until they reselected it.
Which suggests: ship it off by default, say plainly in the setting that it will reset a custom Firefox theme, and only ever touch a window we have actually colored — never call reset() on a window we never touched.
